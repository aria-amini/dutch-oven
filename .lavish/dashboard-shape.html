Where we are / current prototype

What changes / prototype vs real

prototype — now
  • Fixed groups the user can't edit (tonight / weeknight / slow sunday)
  • Synthetic, labeled demo recipes
  • No persistence — one static route
  • No empty state; shelf is always full
  • Rail destinations (pantry / plan / search) are placeholders
real — proposed
  • User-created collections, user-ordered, inline rename/reorder — one group per recipe at first
  • Real recipes from Postgres (Drizzle schema below)
  • Ungrouped recipes allowed; multi-group membership comes later via a join table
  • First-class empty/first-run state — the shelf invites the first save
  • Rail placeholders stay; dashboard only this round

Explicitly out: cooking-in-progress state (deferred by you), social/discovery feeds, nutrition dashboards, any fixed taxonomy, data-entry forms on this surface.

Data model / builder must not invent differently

Current DB is template-only (auth + a placeholder items table). Two new tables now, two deferred. The relationships in plain English:

  • Everything belongs to a user — recipes, collections, and logs each carry your userId.
  • A collection is the group itself — one row per shelf group you make ("weeknight heroes", position 1). Just a name and an order. A recipe sits in one group via its collectionId column.
  • deferred recipe_collections (the membership join table) is only needed when a recipe can live in several groups. Cut from the first build — upgrading later backfills it from collectionId, no data loss.
  • deferred A meal_log would be one row per cooked meal ("ragù, last Tuesday") → the record of the core loop closing: find it, cook it, log it. Cut from the first build — with it go "recently cooked", history, and streaks. Adding it later is a clean append: new table, no migration of existing data.

Decisions / all settled — brief confirmed

1How do recipes get onto the shelf? decided

Manual add now, import-ready. The add flow (title + pick collections) is structured so a URL-import field drops in later without redesign. Import-from-URL stays a separate, later shape.

2What does a recipe tile show? decided

Photo with flat fallback. Real food imagery leads when a recipe has one; ingredient-color tiles cover the rest. Consequence: recipes.imageUrl (nullable) is in the data model above.

3One group per recipe, or several? decided

2 tables — one group per recipe. recipes + collections; a recipe sits in one group via its collectionId column. The join table (recipe_collections) and meal_logs are deferred; both upgrade later without data loss.
